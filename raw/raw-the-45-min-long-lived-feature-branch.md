In the middle of a workshop, we were mobbing with AI doing agentic coding. And suddenly we found that we were having a lot of pain getting our work through. One of our colleagues had started work on a slightly larger revision of the code base and had branched off with a feature branch from our normal trunk-based workflow. This was something that was critically important, and so we paired with him on unblocking it, giving ideas and feedback. The work that we were doing took a bit of a hit. We had to slow down from our trunk-based development so that we didn't force him to rebase every few minutes. We remember having a discussion of the relief of how much easier it was once we'd reviewed the code and merged that feature branch and how painful it had been to work in the repo while knowing that that was looming over us. When we look back, the branch only lived for 45 minutes. This is the story of the 45-minute long-lived feature branch.

We do a lot of workshops with companies looking to build agents and looking to use agentic coding. The structure of these workshops is amazing. It really gets the most out of us and the client. We open with a deep dive into the product and the value map on the first day. This primes everyone to understand the whole domain, the space that we're working in and what the client currently has and where they'd want to get to. but also where their customers get value from their product.

Once we've got the lay of the land, day two and three are about building. We set the time up to have four sprints over the two days. That means we have 10-15 minutes to orientate ourselves at the beginning of the day. Decide what we're going to deliver. Split out and code for two or three hours before coming back together for lunch and then presenting what we delivered in the morning. With another 15 minutes to decide what we're going to build upon that in the afternoon. And a final demo, two to three hours of coding and then a final demo at the end of the day. I'm not certain if I'd want to work like this every day, but the amount that you can achieve in a week is truly astronomical working this way.

This was Sprint 2. By this point we'd already settled into a comfortable rhythm of mobbing, discussing the architecture, occasionally whiteboarding, and then working with AI agents to build the designs that we'd created. We showed each other the code and when we were happy pushed everything up to main, trunk based.
We learn a number of tools or features to implement and we split them out amongst us to be able to work faster in collaboration. The problem came when we decided to refactor the agent to use the bi-directional conversation audio agent rather than a basic standard agent.   This change had a number of knock-on effects that touched many different parts of the code base and hence the engineer working on it wanted to work in a separate branch just to test and deploy separately.
As we continued building out our tools, it became more and more apparent that there was a disconnect between the four of us mobbing. And shortly we started realising that the pieces that we had split off would be touched by this change and so it didn't make a lot of sense forging ahead until this landed. This was the first time that any of us had used the bidirectional agent from strands. So taking a look at the docs, we'd thought some ideas and passed them on to the AI, but the implementation took a couple of attempts than we hoped it would.
We quickly, all four of us quickly mobbed on this and thrashed out which of the potential implementations we felt most positive about and the engineer quickly merged the "long-lived feature branch".We all breathed a sigh of relief and got back to working on our individual features as soon as CI had passed. Quickly rebasing and bringing all of the upstream changes into our local. In the end we had pretty minor conflicts and we were joking about how in the current paradigm 45 minutes is a long time to not have to merge to main.

The thing that really surprised me about the whole thing was that we all agreed that that wasn't the way. Before, when I've worked in trunk-based development, teams have been very worried about not using PRs or having dedicated formal code review as opposed to asynchronous code review or live code review. But doing it this way felt really slow and painful to us and we felt that lack of productivity with the engineers not working on the feature branch.For me it's super interesting that these techniques that have been around for ages are only becoming more and more important with the rise of AI-assisted coding.The reason we were able to go fast was twofold. Firstly, this was a throwaway proof of concept. That certainly helps. However, just to make it go faster, we decided to add tests in CI/CD so that we knew that the pieces that we had already worked on weren't going to get erased and we weren't going to get any regressions from pieces we'd already built. We also set up a clear architecture, which was a shared context between the humans in the room, which was incredibly important to ensure that when we were working on the codebase and collaborating with the AI, we already had a shared knowledge and understanding of what we were trying to build. One of the really validating things after one of the sprints was using like C4 to sketch out the architecture that we had and it exactly matched what we'd drawn on one of the whiteboards.For me the key part there was the shared context that the humans had in their heads. By looking at the code and understanding the architecture, we were able to remove all of the duplication and complication that is sometimes introduced when using AI code generation tools.
